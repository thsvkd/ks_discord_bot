- 대상: `ks_bot/core/scoring.py` (+ `ks_bot/core/pubg.py`, `ks_bot/cogs/balancer.py` 일부)
- 상태: **설계안**. 이 문서는 구현을 포함하지 않는다.
- 목표: `/점수`가 내놓는 숫자를 "실질적인 실력"의 단조 대리지표로 만들고, 모든 상수에 단위와 의미와 재보정 절차를 붙인다.

## 2. 데이터 실사 (읽기 전용 확인 결과)

### 2.1 `Match.participants` 는 점수 계층까지 오지 않는다 — 확인 완료

지시받은 대로 코드로 확인했다. 결론은 **현재 구조에서는 쓸 수 없다**이다.

1. `Match.participants` 는 `Match.from_api()`(`models.py:163`)가 채운다. 여기까지는 로비 전원의 스탯이 들어 있다.
2. 그러나 `PubgBalancer` 는 그걸 즉시 버린다.
   - `get_player_match_stats()` (`pubg.py:183-186`): `fetch_match()` → `match.player_stats(player_name)` → 본인 `PlayerMatchStats` 만 upsert.
   - `get_latest_player_match_stats_list()` (`pubg.py:212-214`): 동일.
3. 저장소 스키마 `player_match_stats`(`repository.py:47-78`)에는 로비 관련 컬럼이 하나도 없다. `Match` 자체를 저장하는 테이블도 없다.
4. 결정적으로, **캐시 히트 경로는 매치 API를 아예 호출하지 않는다**(`pubg.py:202`의 `get_player_match_stats_bulk`). 즉 이미 캐시된 매치는 참가자 정보를 되살릴 방법이 없고, 되살리려면 캐시된 전 매치를 재조회해야 한다(유저 1명당 최대 40회 추가 API 호출).

→ **본 설계는 `participants` 에 의존하지 않는다.** 대신 **`kill_place`** 를 쓴다. `kill_place`는 "그 판 로비 안에서 킬 기준 순위"로, PUBG가 이미 계산해 주는 **로비 상대 백분위**이고, 이미 `PlayerMatchStats`에도 DB에도 저장되어 있다(`models.py:90`, `repository.py:62`). 추가 호출도 스키마 변경도 필요 없다.

만약 나중에 정확한 로비 크기가 필요해지면(예: 인원이 60~80명인 비인기 시간대 큐 보정) 다음 변경이 필요하다. 지금은 **채택하지 않는다**.

- `PlayerMatchStats` 에 `participant_count: int`, `roster_count: int` 추가 → `SqliteRepository._migrate_missing_columns()`(`sqlite.py:141-152`)가 `ALTER TABLE ... ADD COLUMN` 을 자동 수행하므로 DDL 작업은 불필요.
- 단, 기존 행은 `NULL` 이 되고 `_row_to_match_stats()`(`repository.py:296-297`)가 `int(value) if value is not None else 0` 으로 읽어 **0** 이 된다. 즉 "미상"과 "0명"이 구분되지 않는다 → 0을 미상으로 보고 모드 기본값으로 폴백해야 한다.
- 또한 `_row_to_match_stats()` 는 `f.type in ('int', int)` 로 분기하는데 `from __future__ import annotations` 때문에 `f.type` 은 문자열이다. `int | None` 타입으로 필드를 추가하면 이 분기에 걸리지 않고 `else` 로 떨어져 잘못 파싱된다. 필드를 추가한다면 **평범한 `int` 로, 0을 미상 취급**해야 한다.

### 2.2 점수는 DB에 저장되지 않는다 — 확인 완료

- `players` 테이블의 `rank_stats` / `normal_stats` 컬럼은 존재하지만, `Player.from_api()`(`models.py:50-64`)가 이 두 필드를 채우지 않아 `upsert_player()`(`repository.py:133-134`)는 **항상 빈 `{}`** 를 기록한다.
- `Stats` 는 어떤 테이블에도 저장되지 않는다. `/점수` 는 매 호출마다 `aggregate_stats()` 로 계산해 임베드에 바로 출력한다(`balancer.py:226-227`).

→ **점수 스케일을 바꿔도 DB 마이그레이션이 필요 없다.** 영향은 표시 문구(임베드 임계값)와 테스트뿐이다.

### 2.3 팀 밸런서는 아직 없다

`ks_bot/cogs/balancer.py` 에 있는 커맨드는 `/점수` 하나뿐이다. `PubgBalancer.fetch_clan()` 과 `DEFAULT_CLAN_ID` 는 있지만 팀을 나누는 코드는 존재하지 않는다. 따라서 "팀 밸런서에 미치는 영향"은 **현재 없다**. 다만 향후 밸런서가 점수를 합산/평균할 것이므로, 새 점수는 **선형 비교와 산술 평균이 의미를 갖는 유계 스케일**이어야 한다는 요구는 설계에 반영했다(0~100).

### 2.4 랭크 API는 이미 있지만 아무도 호출하지 않는다

- `PubgBalancer.fetch_ranked_stats(player_name, season_id)`(`pubg.py:128-134`)와 `Stats.from_ranked_api()`(`models.py:207-225`)가 구현되어 있고 `Tier`/`sub_tier`/`rank_point` 를 채운다.
- `fetch_current_season()`(`pubg.py:121-126`)도 있다.
- 호출부는 `tests/test_network_pubg.py:57` 뿐, 프로덕션 경로 어디에서도 쓰지 않는다.

→ 랭크 매치 처리에 이 두 함수를 **재사용**한다. 신규 API 래퍼를 만들 필요는 없다.

## 3. 설계 원칙

1. **두 축으로 분해한다.** 배틀그라운드의 실력은 (a) 생존/운영 = 어디까지 남는가, (b) 교전력 = 살아있는 동안 얼마나 제압하는가로 나뉜다. 서로 다른 정보를 담으므로 따로 재고 합친다.
2. **모든 항은 `[0, 1]` 유계여야 한다.** 딜 5000짜리 한 판이 평균을 폭파시키지 않게 한다. 유계이면 총점도 유계가 되어 팀 밸런싱에서 안전하다.
3. **상수는 반드시 (단위 · 의미 · 재산출 절차) 세 가지를 갖는다.** "이 값을 넣으면 해당 항이 정확히 0.5가 된다" 처럼 한 문장으로 설명되지 않는 상수는 넣지 않는다.
4. **파라미터 개수를 최소화한다.** 파생 가능한 값은 파생시킨다(§5.4).
5. **가능하면 게임 규칙에서 상수를 끌어온다.** 정원 100명, 체력 100, 스쿼드 4인 같은 값은 튜닝 대상이 아니다.
6. **저장된 데이터만 쓴다.** 추가 API 호출이 필요한 신호(티어)는 실패해도 점수가 나오도록 **선택적**으로 결합한다.

## 4. 지표 선정과 근거

### 4.1 채택

| 필드 | 역할 | 근거 |
| --- | --- | --- |
| `win_place` | 배치 항의 유일한 입력 | 매치의 최종 성과. 모드별 팀 수로 정규화하면 모드 간 비교가 가능하다. |
| `damage_dealt` | 교전 항 주신호 (가중 0.40) | 교전 기여의 연속량이고 표본 분산이 가장 작다. 킬은 정수라 3~4판 표본에서 튀지만 딜은 완만하다. 100(=적 1명분 체력) 단위로 읽으면 물리적 의미도 명확하다. |
| `kills` | 교전 항 (가중 0.25, `takedowns` 구성) | 마무리 능력. 딜만 넣고 못 잡는 플레이어와 구분한다. |
| `DBNOs` | 교전 항 (`takedowns` 구성) | **스쿼드에서 개인 교전력의 진짜 지표**. 눕히는 것이 교전의 본질이고 마무리는 팀 상황/위치 운에 좌우된다(팀원이 뺏어감). 솔로에서는 값이 항상 0이라 자동으로 무시된다 → 모드별 분기 없이 적응한다. |
| `assists` | 교전 항 (`takedowns` 구성, 지분 0.25) | 팀 기여. 다만 정보 대부분이 이미 `damage_dealt` 에 들어 있으므로 중복 방지를 위해 지분을 작게 준다. |
| `time_survived` | 교전 항의 **분모** (분당 딜, 가중 0.20) | 점수 항으로 직접 쓰면 `win_place` 와 상관이 매우 높아 배치 항을 이중 계상한다. 대신 "초반에 죽었지만 딜 200"과 "끝까지 살아서 딜 200"을 구분하는 **효율 지표의 분모**로만 쓴다. 이것이 생존시간의 유일하게 중복되지 않는 용도다. |
| `kill_place` | 교전 항 (가중 0.15) | **로비 상대 킬 순위**. PUBG가 그 판의 100명 기준으로 계산해 주므로 파라미터 없이 로비 난이도가 보정된다. 다만 킬 동률 시 타이브레이크 규칙이 공식 문서에 없어 신뢰도가 낮으므로 가중치를 가장 작게 준다. |
| `revives` | 보너스 (+2점/회, 최대 +4) | 스쿼드/듀오에서 팀 전력 유지의 직접 기여이고 다른 지표에 전혀 반영되지 않는다. 솔로에서는 자연히 0. |
| `team_kills` | 감점 (-5점/회, 최대 -10) | 실력의 반대 신호. 사고든 트롤이든 팀에 순손실이므로 명시적으로 뺀다. |
| `headshot_kills` | 집계 단계 정확도 보정 (±2점) | 에임 지표이긴 하나 매치 단위로는 분산이 지나치게 크다(3킬 중 1헤드 = 33%). **집계 단계에서 총 킬 10 이상일 때만** 헤드샷 비율을 기준선과 비교해 소폭 가감한다. |
| `death_type` | `deaths` 실측 | `'alive'` 이외를 사망으로 센다. 결함 #6 해결. |
| `game_mode` | 모드 정규화 키 | §6. |
| `match_type` | 랭크/일반 분기 | §7. |

| `kill_streaks` | `kills` 와 거의 완전히 중복(연속 킬은 킬 수의 함수). 별도 정보를 주지 않는다. |
| `is_custom_match` | 커스텀 매치는 `MatchType.CUSTOM` 으로 이미 `SCORABLE_MATCH_TYPES` 에서 걸러진다. |
| `Match.participants` | §2.1 — 점수 계층까지 전달되지 않는다. `kill_place` 로 대체. |
| `Match.duration` | `PlayerMatchStats` 로 전달되지 않는다(`models.py:106-134`). 필요한 "기준 시간"은 상수 `REFERENCE_MINUTES = 20` 으로 대체한다. |

## 5. 점수 모델

### 5.1 매치 1건 점수

모드 패밀리 `M ∈ {solo, duo, squad}`, 그 모드의 예상 팀 수 `T[M]`, 로비 정원 `P = 100` 이라 하자.

```
sat(x)      = x / (1 + x)                    # 포화 함수. 파라미터 없음. x=1 → 0.5, x→∞ → 1
clamp01(x)  = min(1, max(0, x))
```

**(a) 배치 항**

```
lin(r)   = (T - r) / (T - 1)                 # 선형 백분위
log(r)   = 1 - ln(r) / ln(T)                 # 로그 백분위 (상위권 가중)
place    = clamp01(0.5 * lin(r) + 0.5 * log(r))       # r = clamp(win_place, 1, T)
place    = 0.0                                        # win_place <= 0 (파손 데이터)
```

**(b) 교전 항**

```
takedowns = kills + 0.75 * max(DBNOs - kills, 0) + 0.25 * assists
dpm       = damage_dealt / (max(time_survived, 60) / 60)
kill_pct  = clamp01(1 - (kill_place - 1) / (P - 1))    # kill_place <= 0 이면 0.0

combat = 0.40 * sat(damage_dealt / DMG_REF[M])
       + 0.25 * sat(takedowns    / TD_REF[M])
       + 0.20 * sat(dpm          / DPM_REF[M])
       + 0.15 * kill_pct
```

**(c) 합성 + 보정**

```
raw   = 0.45 * place + 0.55 * combat
raw  += 0.02 * min(revives, 2)          # 부활 보너스, 최대 +0.04
raw  -= 0.05 * min(team_kills, 2)       # 팀킬 감점, 최대 -0.10
score = 100 * clamp01(raw)              # → [0, 100]
```

### 5.2 왜 이 배분인가

- **`place : combat = 0.45 : 0.55`.** 스쿼드에서 `win_place` 는 4인의 공동 산출물이다. 내가 초반에 죽어도 팀이 치킨을 먹으면 1등이 된다. 즉 배치는 개인 실력에 대한 잡음이 크다. 반면 딜/제압은 온전히 본인 기여다. **개인 실력 측정**이 목적이므로 교전 쪽을 약간 무겁게 둔다. 두 값은 합이 1인 단일 파라미터(`W_PLACE`)로 노출해 한 곳에서만 조정하게 한다.
- **교전 항 내부 가중은 "신뢰도 순"이다.** 딜(0.40) > 제압(0.25) > 효율(0.20) > 로비 킬 순위(0.15). 앞쪽일수록 표본 분산이 작고 의미가 명확하며, 마지막 `kill_place` 는 타이브레이크 규칙이 비공개라 가장 낮다.
- **`KNOCK_SHARE = 0.75`.** 눕혔지만 마무리를 못 한 건(= `DBNOs - kills`) 교전의 본질은 다 한 것이고 막타만 놓친 것이므로, 킬의 3/4 가치로 센다.
- **`ASSIST_SHARE = 0.25`.** 어시스트가 담는 정보(내가 딜을 넣었다)는 이미 `damage_dealt` 에 있다. 이중 계상을 막기 위해 킬의 1/4만 인정한다.
- **`sat(x) = x/(1+x)` 를 쓰는 이유.** 파라미터가 하나도 없고, 단조 증가하며, `[0,1)` 로 유계이고, "기준선을 정확히 달성 = 0.5" 라는 해석이 자연스럽다. `min(x, 1)` 같은 하드 클립은 상위권을 전부 동점으로 만들어 밸런싱에 쓸 수 없다.

### 5.3 등수 항 대안 비교 (요구사항 #4)

스쿼드(`T = 25`) 기준 실제 값:

| `win_place` | 현행 `13.2481/r` | A. 선형 `lin` | B. 로그 `log` | **C. 절반씩 혼합(채택)** |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 13.25 | 1.000 | 1.000 | **1.000** |
| 2 | 6.62 | 0.958 | 0.785 | **0.871** |
| 3 | 4.42 | 0.917 | 0.659 | **0.788** |
| 4 | 3.31 | 0.875 | 0.569 | **0.722** |
| 5 | 2.65 | 0.833 | 0.500 | **0.667** |
| 8 | 1.66 | 0.708 | 0.354 | **0.531** |
| 10 | 1.32 | 0.625 | 0.285 | **0.455** |
| 13 | 1.02 | 0.500 | 0.203 | **0.352** |
| 15 | 0.88 | 0.417 | 0.159 | **0.288** |
| 20 | 0.66 | 0.208 | 0.069 | **0.139** |
| 25 | 0.53 | 0.000 | 0.000 | **0.000** |

- **현행 `1/r`**: 1등→2등에서 값이 반토막 나고, 10등 아래로는 전부 0.5~1.3 구간에 뭉쳐 변별력이 없다. 게다가 꼴등(25등)이 0이 아니라 0.53을 받는다. 기각.
- **A. 선형 백분위**: 모드 정규화가 가장 자연스럽고 전 구간 변별력이 균일하다. 하지만 1등과 2등의 차이가 0.042뿐이라 "치킨"의 가치를 거의 인정하지 않는다. 실제로는 상위권 한 계단이 훨씬 어렵다.
- **B. 로그 백분위**: 상위권 가중이 적절하나 중위권을 과하게 깎는다(11등 = 상위 44%인데 0.255).
- **D. 구간(bin) 매핑** (예: 1등 1.0 / 2~3등 0.8 / 4~10등 0.5 / …): 해석은 쉽지만 경계에서 불연속이라 10등과 11등의 차이가 3등과 10등의 차이보다 커지는 역전이 생기고, 튜닝할 임계값이 모드마다 필요하다. 기각.
- **C. 채택 이유**: A와 B의 결점이 정확히 반대 방향이라 절반씩 섞으면 상쇄된다. 1등(1.000)과 2등(0.871)의 격차가 뚜렷하면서 중위권(13등 0.352)도 하위권(20등 0.139)과 확실히 구분된다. 전 구간 단조·연속이고 `[0,1]` 유계이며, 파라미터는 혼합 비율 0.5 하나뿐이다.

**알려진 한계**: 로그 성분은 `T` 에 의존하므로 모드 간 **동일 백분위 등가가 완전하지는 않다**. 상위 20% 기준으로 솔로 20등 = 0.579, 듀오 10등 = 0.614, 스쿼드 5등 = 0.667 이다(최대 편차 0.09, 스쿼드가 약간 유리). "1등은 어느 모드든 만점" 이라는 성질을 지키면서 백분위 완전 등가를 만드는 것은 불가능하므로, 전자를 택하고 편차는 문서화한다. 현재 수집 대상이 스쿼드뿐(§1)이라 실질 영향은 없다.

_SOLO_MODES = {SOLO, SOLO_FPP, NORMAL_SOLO, NORMAL_SOLO_FPP}

### 6.2 FPP / TPP 는 구분하지 않는다

FPP가 정보량이 적어 딜량 기대치가 다르다는 통념은 있으나 저장소 안에 이를 뒷받침할 데이터가 없고, 큐를 나누면 표본이 반토막 난다(현재 상한이 40판인데 FPP/TPP가 섞인 유저는 각 20판). **동일 취급**하되, 보정 스크립트(§11)는 FPP/TPP를 나눠서도 통계를 찍어 나중에 판단할 수 있게 한다.

### 6.3 정규화가 실제로 하는 일

| | 솔로 | 듀오 | 스쿼드 |
| --- | ---: | ---: | ---: |
| `T` (팀 수) | 100 | 50 | 25 |
| 4등의 배치 항 | 0.834 | 0.792 | 0.722 |

## 7. 랭크 매치 처리

### 7.1 고정 점수 폐기

`RANKED_MATCH_SCORE = 1.2` 를 **삭제**하고, 랭크 매치도 §5의 공식으로 **동일하게** 채점한다. 랭크 매치의 `PlayerMatchStats` 는 일반 매치와 완전히 같은 스키마로 들어온다(`Match.from_api()` 가 `matchType` 만 다르게 넣을 뿐). 별도 취급할 이유가 데이터상 없다.

랭크 로비는 실력대가 좁아 같은 성적을 내기가 더 어렵다. 그래서 매치 점수만 보면 랭크 유저가 약간 손해를 본다. 이 손해는 **배율 상수를 새로 만들어 보정하지 않고**, 아래 티어 결합으로 상쇄한다. 배율은 근거를 댈 수 없는 매직 넘버가 되기 때문이다.

### 7.2 티어 결합

`Tier` / `sub_tier` 는 "그 유저가 도달한 실력대"를 게임이 직접 인증한 값이다. 매치 표본보다 훨씬 긴 기간을 반영하므로 좋은 앵커다.

```
TIER_ORDER = {BRONZE: 1, SILVER: 2, GOLD: 3, PLATINUM: 4, DIAMOND: 5, MASTER: 6}

sub        = (6 - sub_tier) / 5              # PUBG는 subTier 1이 최상위, 5가 최하위 → 1.0 ~ 0.2
                                             # MASTER 등 sub_tier가 없으면 sub = 1.0
tier_score = 100 * (TIER_ORDER[tier] - 1 + sub) / 6      # Bronze5 → 3.3, Master → 100
```

검산: Gold 3 → `100*(2+0.6)/6 = 43.3`. §13의 "중수" 매치 기반 점수 41.4와 거의 일치한다. 두 스케일이 독립적으로 비슷한 값을 내는 것은 사상이 크게 어긋나지 않았다는 방증이다.

**혼합 비중은 랭크 매치 표본 비율에 연동한다:**

```
ranked_ratio = (랭크 매치 수) / (점수화된 전체 매치 수)
lambda       = TIER_BLEND_MAX * ranked_ratio            # TIER_BLEND_MAX = 0.5
final        = (1 - lambda) * match_based + lambda * tier_score
```

| 유저 유형 | `ranked_ratio` | `lambda` | 결과 |
| --- | ---: | ---: | --- |
| 일반만 | 0.0 | 0.00 | 티어를 아예 쓰지 않는다(불필요한 API 호출도 하지 않는다). |
| 반반 | 0.5 | 0.25 | 매치 성적 75% + 티어 25%. |
| 랭크만 | 1.0 | 0.50 | 매치 성적 50% + 티어 50%. **결함 #1 해결** — 이제 랭크 유저도 성적에 따라 점수가 달라지고, 티어까지 반영된다. |

**티어를 못 가져오면 `lambda = 0`.** 티어 조회는 `fetch_current_season()` + `fetch_ranked_stats()` 두 번의 추가 API 호출이 필요하다(`pubg.py:121,128`). 다음 규칙을 지킨다.

- `ranked_ratio == 0` 이면 아예 호출하지 않는다.
- 시즌 ID는 프로세스 수명 동안 메모리 캐시한다(시즌은 몇 달에 한 번 바뀐다).
- 실패(`PlayerMatchStatsNotFoundError`, 레이트 리밋, 언랭크)는 **`logger.info` 후 `lambda = 0` 폴백**. 점수 조회 자체가 실패해서는 안 된다.
- `Tier.UNRANKED` / `Tier.UNDEFINED` 도 `lambda = 0`.
- `fetch_ranked_stats()` 는 `squad` 랭크 통계만 읽는다(`pubg.py:131`). 현재 매치 수집도 스쿼드 전용이므로 정합적이다. 다른 모드로 확장할 때 함께 손봐야 한다.

`Stats.tier` / `Stats.sub_tier` / `Stats.rank_point` 필드는 이미 존재하므로(`models.py:185-187`) 결과에 그대로 채워 넣어 임베드에서 함께 보여줄 수 있다.

`rank_point` 는 **쓰지 않는다.** 티어별 RP 구간이 시즌마다 바뀌고 공식 문서화가 없어 상수를 만들 근거가 없다. 티어+서브티어 서수만으로 충분한 해상도(30단계)가 나온다.

## 8. 표본 수 보정

경험적 베이즈 축소(shrinkage)를 쓴다.

```
base   = mean(매치 점수)
shrunk = (n * base + PRIOR_WEIGHT * PRIOR_SCORE) / (n + PRIOR_WEIGHT)
```

- `PRIOR_SCORE = 40.0` — 모델이 중위권 표본에 대해 산출하는 값(§13에서 실측). "모르면 평범하다고 본다".
- `PRIOR_WEIGHT = 5.0` — "사전 믿음이 매치 5판만큼의 무게를 갖는다". 최소 표본 요건 20판에서 실측치가 80% 지분을 갖도록 잡았다. 매치 점수의 표준편차를 20점 정도로 볼 때 n=5면 표준오차가 약 9점이라 이 지점에서 반반 섞이는 것이 타당하다.

| n | 원점수 65 → | 원점수 20 → |
| ---: | ---: | ---: |
| 1 | 44.2 | 36.7 |
| 2 | 47.1 | 34.3 |
| 5 | 52.5 | 30.0 |
| 10 | 56.7 | 26.7 |
| 20 | 60.0 | 24.0 |
| 40 | 62.2 | 22.2 |

표본이 커질수록 양쪽 모두 원점수에 단조로 접근한다. 1~2판만 있는 유저는 사전분포(40) 근처에 머물러 "치킨 한 판 먹고 최고 등급"이 나오지 않는다. **결함 #7 해결.**

**부수 효과 — 최소 매치 수 요건 완화(선택).** 현재 `PubgBalancer.required_match_num = max(1, max_match_num // 2)` = 20판 미만이면 `NotEnoughMatchesError` 로 아예 거부한다(`pubg.py:66-68, 240-241`). 축소 보정이 들어가면 표본이 적어도 점수가 폭주하지 않으므로 이 하한을 5판 정도로 낮추고, 대신 임베드에 "표본 N판" 을 함께 표기하는 것이 사용자 경험상 낫다. **다만 이는 동작 변경이므로 기본값은 유지하고 별도 결정 사항으로 남긴다.**

**최근성 가중은 이번 범위에 넣지 않는다.** `player.match_ids` 가 최신순이라 지수 감쇠(반감기 ~20판)를 적용하기는 쉽지만, 파라미터가 하나 늘고 검증 시나리오가 복잡해진다. §15에 확장안으로 기록한다.

## 9. 집계(`aggregate_stats`) 개편

```python
def aggregate_stats(matches: Sequence[PlayerMatchStats], *, ranked: Stats | None = None) -> Stats: ...
```

1. **`deaths` 를 실측으로 바꾼다.**
   ```python
   ALIVE_DEATH_TYPES = frozenset({'alive'})
   deaths = sum(1 for m in matches if m.death_type and m.death_type not in ALIVE_DEATH_TYPES)
   ```
   `death_type` 이 빈 문자열인 행(구 캐시/파싱 실패)만 기존 근사 `win_place != 1` 로 폴백한다. **결함 #6 해결.**
   PUBG가 쓰는 값은 `alive` / `byplayer` / `byzone` / `suicide` / `logout` 이다. `logout`(게임 이탈)은 비정상 종료라 표본에서 빼는 것도 합리적이지만, 이탈 자체가 실력 신호일 수 있고 빈도가 낮아 **이번에는 그대로 사망으로 센다**(문서화된 결정).
2. **`kda` 는 새 `deaths` 로 계산한다.** `Stats.kd` 프로퍼티도 자동으로 정확해진다.
3. **`top10_ratio` 는 모드 정규화한다.** 스쿼드에서 "10등 이내"는 25팀 중 상위 40%라 무의미하다. **상위 10% 비율**(`win_place <= max(1, round(T * 0.1))`)로 바꾼다. 스쿼드는 상위 2~3등, 솔로는 상위 10등이 된다. 필드 이름(`top10_ratio`)은 유지하되 docstring에 정의를 적는다.
4. **헤드샷 정확도 보정**을 여기서 적용한다.
   ```python
   if kills >= HEADSHOT_MIN_KILLS:
       hs_ratio = headshot_kills / kills
       adjust = clamp(HEADSHOT_SWING * (hs_ratio - HEADSHOT_BASE) / HEADSHOT_BASE, -HEADSHOT_SWING, +HEADSHOT_SWING)
   ```
5. **티어 결합**(§7)을 적용하고 `tier` / `sub_tier` / `rank_point` 를 결과에 채운다.
6. 최종 `clamp(0, 100)`.

**계산 순서 (고정)**

```
매치별 점수 → 산술 평균 → 표본 축소 → 헤드샷 보정 → 티어 혼합 → clamp(0, 100)
```

축소를 티어 혼합보다 **먼저** 하는 이유: 티어는 표본 수와 무관하게 이미 신뢰할 수 있는 값이므로 축소 대상이 아니다. 매치 기반 성분만 축소한 뒤 섞어야 "판수가 적은 랭크 유저"가 티어 쪽으로 자연스럽게 수렴한다.

## 11. 상수 재보정 절차

`DMG_REF`, `PRIOR_SCORE`, `HEADSHOT_BASE` 는 "우리 서버 유저 분포"에 의존한다. 잠정값은 위 표대로 두되, **로컬 캐시 DB에서 재산출하는 스크립트**를 함께 만든다. 이것이 "매직 넘버 금지"의 실행 장치다.

`scripts/calibrate_scoring.py` (신규, 네트워크 접근 없음):

1. `settings.db_path` 의 `player_match_stats` 를 읽는다.
2. `match_type IN ('official', 'competitive')` 로 거르고 `game_mode` 를 패밀리로 묶는다. FPP/TPP는 나눠서도 한 번 더 출력한다.
3. 패밀리별로 출력한다:
   - `damage_dealt` 의 p50 / **p75** / p90 → **`DMG_REF[M]` 권장값 = p75**
     ("기준선을 정확히 달성하면 항이 0.5" 라는 정의상, 상위 25% 수준을 기준선으로 잡는다. 그러면 중위 플레이어의 딜 항은 `sat(p50/p75)` ≈ 0.37 로 자연스럽게 0.5 아래에 놓인다.)
   - `time_survived` 의 p75(분) → `REFERENCE_MINUTES` 검증
   - `headshot_kills / kills` 총합 비율 → `HEADSHOT_BASE`
   - 매치 점수 분포의 p50 → `PRIOR_SCORE`, 표준편차 → `PRIOR_WEIGHT` 감각 확인
4. 계산된 값으로 §13의 페르소나 점수를 다시 찍어 순서와 대역이 유지되는지 보여준다.

스크립트는 **값을 자동으로 덮어쓰지 않는다.** 권장값을 출력만 하고, 상수 수정은 사람이 커밋한다(값이 조용히 바뀌면 점수 변동 원인을 추적할 수 없다).

## 13. 검증 시나리오

스쿼드 매치 10판, 각 판의 스탯이 아래 값으로 **일정**하다고 가정한다(테스트에서는 동일 매치를 10개 복제하면 된다). `revives = 0`, `team_kills = 0`, `headshot_kills = 0`, `death_type = 'byplayer'` 로 고정.

| 페르소나 | `win_place` | `damage_dealt` | `kills` | `DBNOs` | `assists` | `time_survived` | `kill_place` |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 초보 `rookie` | 19 | 80 | 0 | 0 | 0 | 500 | 75 |
| 중수 `average` | 11 | 230 | 2 | 2 | 1 | 1100 | 35 |
| 고수 `skilled` | 4 | 450 | 4 | 5 | 2 | 1500 | 8 |
| 프로 `pro` | 2 | 700 | 7 | 8 | 2 | 1700 | 3 |

### 13.1 매치 1건 점수 (축소 보정 전)

| 페르소나 | 배치 항 | 교전 항 | **매치 점수** |
| --- | ---: | ---: | ---: |
| 초보 | 0.168 | 0.174 | **16.9** |
| 중수 | 0.419 | 0.412 | **41.5** |
| 고수 | 0.722 | 0.588 | **64.8** |
| 프로 | 0.871 | 0.679 | **76.6** |

### 13.2 10판 표본의 최종 점수 (축소 보정 후, 티어 없음)

`shrunk = (10 * base + 5 * 40) / 15`

| 페르소나 | 매치 점수 | **최종 점수** | 임베드 등급 |
| --- | ---: | ---: | --- |
| 초보 | 16.9 | **24.6** | 애송이로군요! |
| 중수 | 41.5 | **41.0** | 좀 치는 녀석이군... |
| 고수 | 64.8 | **56.5** | 이, 이녀석 조심해야겠어...! |
| 프로 | 76.6 | **64.4** | 이, 이녀석 조심해야겠어...! |

40판 표본(`(40*base + 200)/45`)이면 각각 **19.4 / 41.3 / 62.1 / 72.6** 이 되어 프로가 최고 등급에 들어간다. 즉 **최고 등급은 충분한 표본을 요구한다** — 의도된 성질이다.

### 13.3 구현 태스크가 테스트로 고정해야 할 어서션

```
# 순서 (허용오차 없이)
rookie < average < skilled < pro

# 간격 (표본 10판 기준) — 실측 16.4 / 15.6 / 7.9
average - rookie >= 12.0
skilled - average >= 12.0
pro     - skilled >=  5.0

# 대역 (표본 10판 기준, 실측값 ±3.0)
rookie  ∈ [21.6, 27.6]    # 실측 24.6
average ∈ [38.0, 44.0]    # 실측 41.0
skilled ∈ [53.5, 59.5]    # 실측 56.5
pro     ∈ [61.4, 67.4]    # 실측 64.4

# 유계
0.0 <= score <= 100.0   (모든 페르소나)
```

허용오차 ±3.0은 상수 재보정(§11)이 소폭 일어나도 테스트가 깨지지 않게 하되, 모델이 근본적으로 바뀌면 잡히도록 잡은 값이다. **순서 어서션은 허용오차 없이 엄격하게** 둔다.

### 13.4 랭크 시나리오

"중수" 스탯으로 **랭크 매치만 10판**, 시즌 티어가 `Diamond / subTier 5` 인 유저:

```
match_based = 41.0                              # 13.2와 동일
tier_score  = 100 * (5 - 1 + (6-5)/5) / 6 = 70.0
lambda      = 0.5 * (10/10) = 0.5
final       = 0.5 * 41.0 + 0.5 * 70.0 = 55.5
```

현행 로직에서 이 유저의 점수는 **`1.2` 고정**이었다. 이것이 결함 #1이 해결됐다는 가장 명확한 증거이므로 테스트로 고정한다.

### 14.2 주의사항

- **봇을 실행하지 말 것.** 이 저장소는 Windows에서 봇을 띄우면 안 된다(운영은 Pi). 검증은 `uv run pytest` 로만 한다.
- **`uv run pytest` 는 기본적으로 네트워크 테스트를 제외한다**(`pyproject.toml` 의 `addopts = "-m 'not network'"`). 티어 결합을 검증할 때 실 API를 부르지 말고 `_request` 를 모킹하라(`tests/test_pubg.py` 의 `build_api` 패턴 참고).
- **`sub_tier` 방향을 반드시 확인하라.** 본 설계는 "PUBG는 subTier 1이 최상위" 를 전제한다. `tests/test_network_pubg.py` 를 `-m network` 로 한 번 돌려 실제 응답으로 확인하고, 다르면 `sub` 식을 뒤집어라. 이 전제가 틀리면 티어 점수가 통째로 뒤집힌다.
- **`kill_place` 의 동률 처리 규칙은 비공개다.** 그래서 가중치를 0.15로 낮게 뒀다. 실데이터에서 이상 분포가 보이면 가중치를 교전 항의 다른 성분으로 재분배하면 되고, 다른 항은 영향받지 않는다.
- **`DBNOs` 는 솔로에서 항상 0** 이다. `takedowns` 식이 자동으로 축약되므로 모드별 분기를 넣지 말 것. 분기를 넣으면 테스트 M4가 잡아낸다.
- **`_row_to_match_stats()` 의 타입 분기**(`repository.py:296-299`)는 `f.type` 문자열 비교다. 어떤 이유로든 `PlayerMatchStats` 에 필드를 추가하게 되면 `int | None` / `float | None` 을 쓰지 말고 평범한 `int` / `float` 로 선언하라(§2.1). **본 설계는 필드 추가를 요구하지 않는다.**
- **`SCORABLE_MATCH_TYPES` 는 그대로 둔다.** 랭크를 다르게 채점하지 않게 되었을 뿐, 어떤 매치를 세는지는 바뀌지 않는다.
- **부동소수 비교는 `pytest.approx`** 로. 단조성 테스트는 `>` 를 쓰되 값 차이가 충분히 크게 입력을 잡아라(1e-9 수준 차이로 통과시키면 회귀를 못 잡는다).
- **ruff**: line-length 150, 작은따옴표, 한국어 주석. `uv run ruff check` / `uv run ruff format --check` 로 확인.
- **상수는 모듈 최상단에 모으고 각각 한 줄 주석으로 단위와 의미를 적어라.** 이 문서의 §5.4 표가 그대로 주석이 되어야 한다. 주석 없는 리터럴을 다시 만들면 이 재설계의 의미가 없다.
